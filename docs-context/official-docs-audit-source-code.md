# Official Docs Audit Against Swift Source

## Review

- Correct: The docs accurately describe the core scanned paths for Pi resources. `reference/file-locations.md` lists global/project settings and env files, agent/chain/skill/prompt locations, and app data paths; these match `PiScanner.scan(...)`, which constructs `~/.pi/agent/settings.json`, `PROJECT/.pi/settings.json`, `~/.pi/agent/.env`, `PROJECT/.pi/.env`, `~/.pi/agent/agents`, `PROJECT/.pi/agents`, `~/.agents`, `PROJECT/.agents`, chain directories, skill directories, and prompt directories (`pi-manager/PiScanner.swift:7-27`).
- Correct: Native bridge tool names in `reference/native-subagent-bridge.md` match the generated bridge handling. The docs list `managed_subagent`, `managed_chain`, `managed_parallel`, `list_supervisor_requests`, `answer_supervisor_request`, `set_session_plan`, and `update_session_plan` (`pi-documentation/official-documentation/reference/native-subagent-bridge.md:7-15`); the Swift runner dispatches exactly those bridge UI requests (`pi-manager/PiAgentRunnerService.swift:746-772`). The child `contact_supervisor` kinds also match the generated TypeScript enum (`pi-manager/PiNativeSubagentBridgeExtensions.swift:229-234`, `pi-manager/PiNativeSubagentBridgeExtensions.swift:240-263`).
- Correct: The docs' caveat that native child sessions disable ambient extension discovery is supported by source: child runs add `--no-extensions` before any explicit agent extensions and add the child bridge only when `contact_supervisor` is requested (`pi-manager/PiSubagentRunService.swift:59-68`, `pi-manager/PiSubagentRunService.swift:554-558`). Read-first path safety is also accurately documented: absolute paths and `..` are dropped, and paths must remain under the project/worktree root (`pi-manager/PiSubagentRunService.swift:637-645`).
- Correct: GitHub docs are broadly accurate. The app uses `gh auth status --json hosts` and `gh auth token --hostname ...` to discover auth/token state (`pi-manager/GitHubCLIAuthService.swift:10-61`), then uses REST services for issue search/details and git shelling for repository changes as documented.

- Blocker: `user-guide/agents.md` and resource-scope overview docs overstate package-owned agent support. `user-guide/agents.md:11` says builtin agents may be “app-bundled starter agents or package-owned agents,” and `concepts/resource-scopes-and-resolution.md:9-14` / `user-guide/overview.md:41` imply package-owned builtin resources generally. In source, builtin agents are only loaded from `bundled-agents/` (`pi-manager/PiScanner.swift:29`, `pi-manager/PiScanner.swift:129-137`), while `resolveAgents` considers builtin, legacy/global, project, and overrides only (`pi-manager/PiScanner.swift:785-818`). I found package scanning for skills/prompts/extensions, not package agent files. The docs should either remove “package-owned agents” for agents or add a caveat that package-owned agents are not currently scanned as agent definitions by Pi Manager.
- Blocker: Report-only native subagent safety is documented as stronger than the code enforces. `user-guide/native-subagents.md:49` says report-only children “must not edit project files,” and `recipes/run-native-subagent.md:13` repeats this. The source passes this as prompt text only (`pi-manager/PiSubagentRunService.swift:603-605`); it still launches the child in the project/worktree cwd (`pi-manager/PiSubagentRunService.swift:156-158`) and passes through the agent’s configured tools unchanged except `contact_supervisor` filtering (`pi-manager/PiSubagentRunService.swift:548-551`). Important caveat missing: report-only is an instruction/safety contract, not a sandbox or automatic removal of mutating tools.

- Note: Global agent activation docs are slightly incomplete. `reference/file-locations.md` lists global active agents as `~/.pi/agent/agents/*.md` and legacy global as `~/.agents/*.md` (`pi-documentation/official-documentation/reference/file-locations.md:23-25`), which is true for scanning. But when Pi Manager creates/enables a global agent link, it writes to `~/.agents/<name>.md` if `~/.agents` already exists, otherwise to `~/.pi/agent/agents/<name>.md` (`pi-manager/AppViewModel.swift:3304-3309`). The docs should mention this write-target fallback anywhere users are told where global agent links are created.
- Note: Bridge extension file locations are underspecified. `reference/file-locations.md` says native bridge extensions are “generated under Pi Manager Application Support” (`pi-documentation/official-documentation/reference/file-locations.md:61-67`), but the actual path is `~/Library/Application Support/Pi Manager/Native Subagent Extensions/managed-subagent-bridge.ts` and `contact-supervisor-bridge.ts` (`pi-manager/PiNativeSubagentBridgeExtensions.swift:12-19`). Since bridge tools are a focus area, the exact subdirectory and filenames would be useful.
- Note: Pi Agent input modes have a source-code caveat not reflected in user docs: when a session is active, any send is coerced to steering behavior regardless of the selected mode (`pi-manager/PiAgentRunnerService.swift:76-85`). This is probably intentional, but docs that describe follow-up/steer behavior should mention that active streams receive steering and queued follow-up applies when not actively streaming.
